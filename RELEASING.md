# Releasing Dockmesh

`CHANGELOG.md` is generated by [changie](https://changie.dev) from `.changes/` and embedded in
the server, which shows the running version's section as "what's new". Pull requests add
fragments under `.changes/unreleased/`; a release turns them into a version section.

changie is a Go program; run it pinned, as CI does:

```bash
alias changie='go run github.com/miniscruff/changie@v1.26.0'
```

## Testing a release

Every release candidate is installed and exercised on lab VMs before it is tagged: a server, two
agent hosts and the backup targets (local, SMB, SFTP, WebDAV, S3).

1. Take a snapshot of every lab VM (`vzdump` or a Proxmox snapshot) before you start, so each
   check can begin from a known state and a failed upgrade can be rolled back.
2. For a minor release (`X.Y.0`) run the full suite: fresh install of the server and agents,
   enrollment, stack deploy and update, reverse proxy, backups and restores against every target
   type, SSO sign-in, alerts and notifications, and the upgrade from the previous release with
   its data in place.
3. For a patch release run the checks for the areas the release changes and their neighbours,
   plus the upgrade from the previous release.
4. A check you skip or change gets a written reason in the release PR's notes for the reviewer.
   A failing check blocks the tag until it is fixed or explained.

## Security advisories

If the release fixes a vulnerability, prepare a GitHub Security Advisory for the repository
before tagging: affected versions, the permission an attacker needs, impact, workaround and the
fixed version. Add a `Security` fragment that names the issue and links the advisory, then
publish the advisory together with the release.

## Cutting a release

In a release PR (title `release: vX.Y.Z`, label `no-changelog`):

1. Read the fragments in `.changes/unreleased/` and fix wording there.
2. For a minor release (`X.Y.0`) add three or four Highlights:
   `changie new --kind Highlights --body "..."`. The changelog check refuses a minor release
   without them.
3. Optionally write the release summary to `.changes/unreleased/header.md`: plain text, and a
   line `Minimum upgrade from: X.Y.Z` if older versions can't upgrade directly.
4. Batch and merge, with the severity (`security`, `recommended` or `normal`):

   ```bash
   CHANGIE_SEVERITY=recommended changie batch vX.Y.Z --header-path header.md
   changie merge
   ```

   `batch` moves the fragments into `.changes/vX.Y.Z.md`; edit that file if something still
   needs changing and run `changie merge` again. Leave out `--header-path` without a summary.
5. Commit `.changes/` and `CHANGELOG.md` together. CI fails when `CHANGELOG.md` doesn't match
   what `changie merge` generates.

After the release PR is merged, tag the merge commit (`git tag vX.Y.Z && git push origin vX.Y.Z`).
The release workflow renders the notes and `release-manifest.json` from the tag's section with
`scripts/relmanifest` and fails before building if the section is missing.

Once the release is published as the new latest release, the workflow triggers the website's
`release-sync` workflow, which syncs the docs from the tag and puts the new version on
dockmesh.dev. If that trigger fails, the release still succeeds and the run shows a warning.
Run the sync by hand then:

```bash
gh workflow run release-sync.yml -R Dockmesh/website -f tag=vX.Y.Z
```

The trigger uses the `WEBSITE_DISPATCH_TOKEN` secret, a fine-grained token limited to
`Dockmesh/website` with Contents read and write. It expires after a year; renew it before then.

## Pre-releases

A release candidate `vX.Y.Z-rc.N` is a real, installable build for testing the next release, the
update path from one candidate to the next included, without offering it to anyone who didn't
ask for it. Only the maintainer tags candidates; no release PR is needed and nothing in
`.changes/` or `CHANGELOG.md` changes.

```bash
git fetch origin
git tag v0.6.0-rc.1 origin/main && git push origin v0.6.0-rc.1
```

For a candidate the release workflow:

- accepts only the form `vX.Y.Z-rc.N`; other pre-release tags such as `-beta.1` are refused,
  and the commit must be on its release line like any other tag;
- builds the notes and `release-manifest.json` from the fragments in `.changes/unreleased/` at
  the tagged commit, with `"prerelease": true` in the manifest; the Highlights a minor needs
  come with the release PR, so a candidate doesn't need them yet;
- builds, packages and checksums every asset exactly as for a release;
- publishes a GitHub pre-release that never becomes latest, whatever its number, and skips
  the get.dockmesh.dev cache purge and the website sync.

get.dockmesh.dev, `install.sh` without `--version` and the stable update channel therefore
keep pointing at the latest stable release. A candidate is installed with its own installer:

```bash
curl -fsSL https://github.com/Dockmesh/dockmesh/releases/download/v0.6.0-rc.1/install.sh \
  | sudo bash -s -- --version v0.6.0-rc.1
```

To test the update path from rc.N to rc.N+1:

1. Install rc.N on a lab server as above (or upgrade the lab's current release to it) and
   enroll the agents.
2. In Settings › Updates set the update channel to Pre-release and save. The setting is
   audited.
3. Tag rc.N+1. After the workflow has published it, press Check now: the page offers rc.N+1
   with the install command pinned to that version. Run it on the server, then update the
   agents from the Hosts page; agents always move to the server's version.
4. Check that a server on the Stable channel next to it is not offered the candidate.

When the final `vX.Y.0` is out, installs on either channel are offered it, also those still
running a candidate of it. Move lab servers back to Stable when testing is done.

## Patch releases from release/0.5.x

While `main` moves toward the next minor, fixes for the previous one are released from its
branch, `release/X.Y.x` (now `release/0.5.x`). The steps below use 0.5 as the example. Release PR
branches keep a `v` in their name (`release/v0.5.4`) so they don't match `release/*.x`. The branch has the same rules as `main`: changes only by pull request
through the merge queue, `ci-ok` required, squash merges, linear history. CI and CodeQL run for
pull requests, merge-queue runs and pushes on it like on `main`.

1. **Fix on `main` first** when the bug exists there too, with its changelog fragment as usual.
2. **Backport by pull request** to `release/0.5.x`: branch from it, cherry-pick the squash
   commit from `main` (`git cherry-pick -x <sha>`) and open the PR against `release/0.5.x`. The
   fragment comes along with the commit; if the fix differs on the branch, adjust or add the
   fragment there. A fix that only applies to 0.5.x goes straight to the branch with its fragment.
3. **Release PR on the branch** (`release: v0.5.N`), exactly as in "Cutting a release", then tag
   the merge commit on the branch:

   ```bash
   git fetch origin
   git tag v0.5.N origin/release/0.5.x && git push origin v0.5.N
   ```

   The release workflow refuses a `vX.Y.N` tag whose commit isn't on `release/X.Y.x`, or on
   `main` if that branch doesn't exist.
4. **Security advisories** work as described above; the advisory names the fixed patch version
   (and the minor that also contains the fix).
5. **Forward-port the changelog** to `main` in a PR: copy `.changes/v0.5.N.md` from the branch,
   delete the fragments under `.changes/unreleased/` on `main` that went into that patch, and run
   `changie merge`. The next minor then doesn't list the same fixes again.

Only the highest stable version becomes GitHub's latest release. A `v0.5.N` tagged after a
`v0.6.x` is published is a normal release with its assets, but it does not become latest, so
get.dockmesh.dev, `install.sh` without `DOCKMESH_VERSION` and the in-app update check keep
pointing at 0.6.x, and the workflow skips the cache purge and the website sync. Don't run
`release-sync` by hand for such a patch: it would put the older version on dockmesh.dev. Users
who stay on 0.5.x install the patch with `DOCKMESH_VERSION=v0.5.N`; the update check only ever
offers the latest release.

The workflows run from the tagged or pushed commit, so the branch must carry the current
`.github/workflows/` and `scripts/relmanifest`; backport changes to either like any other fix.
