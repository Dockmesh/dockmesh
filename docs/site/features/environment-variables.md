---
title: Environment variables
description: How a stack's .env and the server-wide global variables are combined, where they apply, and how they are stored.
---

Dockmesh has two sources of variables for `${VAR}` substitution in `compose.yaml`:

- the stack's own `.env`, edited on the stack's **Environment** tab;
- **global variables**, edited on the **Environment** page in the sidebar and shared by all stacks.

Both are used only to fill in `${VAR}` references when the compose file is parsed. They are not passed into containers by themselves. To give a container a variable, reference it in the service:

```yaml
services:
  app:
    image: ghcr.io/acme/app:1.4.2
    environment:
      TZ: ${TZ}
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
```

Compose defaults work as usual, for example `${LOG_LEVEL:-info}`.

## The stack .env

Open a stack and go to the **Environment** tab. Each row is a `KEY=value` line; **Add variable** adds one, **Save** writes the file. The **Scope** column shows which services use the key. Keys whose name contains `password`, `secret`, `token`, `api_key`, `credential` or `access_key` are masked in the table until you click **Show secrets**.

You can also edit the file on the server, as long as encryption is off (see below). Changes are picked up at the next deploy.

## Global variables

The **Environment** page (needs `system.update`) holds variables for all stacks, grouped by a free-form **Group** name.

- **Add variable** creates one. Keys are upper-cased and may contain `A-Z`, `0-9` and `_`.
- **Templates** adds common sets with one click: `TZ`, `PUID`, `PGID`, `UMASK`; database, SMTP and proxy settings. Adjust the values afterwards; `TZ` defaults to `Europe/Vienna`.
- **Bulk import** takes the contents of a `.env` file and creates one variable per line in a group you name. Comments and blank lines are skipped, keys that already exist are skipped too.

Deleting a variable that stacks still reference is not blocked. The page does not show references; the API does (`refs_count` in the list, and `GET /api/v1/global-env/{id}/refs` for the stack names), so check there before you remove a shared variable.

## Precedence

When both define the same key, the stack's `.env` wins over the global variable. Internally, Dockmesh puts the global variables first and the stack's lines after them, and the last definition of a key counts.

## Where global variables apply

Global variables are merged in only on some deploy paths:

| Action | Stack `.env` | Global variables |
|---|---|---|
| **Deploy** from the stack page or API | yes | yes |
| Prerequisite deployed through a [dependency](./stacks.md#dependencies-between-stacks) | yes | yes |
| **Roll back** | yes | yes |
| Template deploy | yes | yes |
| Deploy with an environment override active | yes | no |
| Git auto-deploy | yes | no |
| Scale, rolling update, auto-scaling | yes | no |
| Stack migration | yes | no |

Where global variables do not apply, a `${VAR}` that only exists globally resolves to an empty string. If you rely on global variables, deploy those stacks by hand, and do not combine them with overrides or git auto-deploy. Overrides are described in [Environment overrides](../concepts/stacks.md#environment-overrides).

## Storage and encryption

<!-- update after: rbac: scope read endpoints, limit grants, gate sensitive downloads -->
The stack `.env` is encrypted at rest when secrets encryption is on (`DOCKMESH_SECRETS_ENCRYPT_ENV`, default `true`): Dockmesh stores it as `.env.age`, encrypted with the age key `secrets.age-key` in the data directory. With encryption off it is a plaintext `.env` with mode `0600`. Users with `stacks.view` can read the decrypted values through the API.

The values exist in plaintext in these places as well:

- the temporary staging directory during a deploy (removed afterwards);
- the copy of the stack an agent keeps on a remote host (`.env`, mode `0640`);
- `compose.yaml` itself, for values generated by [templates](./templates.md);
- deploy history entries made with an environment override active, because the stored compose has the values filled in.

**Global variables are not encrypted.** They are stored in plaintext in the SQLite database and returned in plaintext to users with `system.update`. Variables created through the API with `"encrypted": true` show an **encrypted** badge and a masked value in the list, but that is a display flag only; the value itself is stored unencrypted. Editing such a variable in the UI clears the flag. Keep real secrets in the stack `.env`, not in global variables, and protect the database file and its backups.

Back up `secrets.age-key`. Without it, every `.env.age` is unreadable; see [Backups](../operations/backups.md).

## API

| Method and path | Permission |
|---|---|
| `GET`, `POST /api/v1/global-env` | `system.update` |
| `PUT`, `DELETE /api/v1/global-env/{id}` | `system.update` |
| `GET /api/v1/global-env/groups` | `system.update` |
| `GET /api/v1/global-env/{id}/refs` | `system.update` |

The stack `.env` is part of the stack and is written with `PUT /api/v1/stacks/{name}` (`stacks.update`). See [API](../reference/api.md).
